# 测试、构建、交付与依赖检查标准

目标是判断团队能否快速、可信、可重复地改变和发布系统，而不是追求某个通用覆盖率数字。

## 目录

1. 行为安全网
2. 测试反馈质量
3. 构建可重复性
4. CI 质量门
5. 发布与回滚
6. 依赖与供应链
7. 开发者工作流
8. 证据与结论

## 1. 行为安全网

检查：

- 核心业务规则、关键旅程和高损失失败是否有自动化验证。
- 无单元测试的遗留路径是否至少有特征测试、黄金主流程或契约测试。
- 测试是否断言有意义的输出和不变量，而不只断言“没有抛错”。
- 失败测试是否稳定复现；随机、时间、网络和并发是否受控。
- mock 是否复制实现细节，导致重构时大量无业务意义的测试破裂。
- 集成边界是否用真实协议/数据库验证，而不是全部模拟。
- 数据迁移、回滚、版本混跑和灾难恢复是否可测试。

按风险分配测试层级。金额、权限、状态机适合细粒度规则测试；数据库方言、序列化和队列语义需要真实集成测试；关键用户旅程保留少量端到端测试。

## 2. 测试反馈质量

记录：

- 本地最小测试、提交级测试和完整套件耗时
- flaky 比例、隔离方式和责任人
- 失败信息是否能定位原因
- 测试数据创建与清理成本
- 并行执行时的共享状态冲突
- 被跳过、禁用或标记预期失败的测试及期限

覆盖率只用于发现未观测区域。结合变更频率、缺陷史、复杂度和业务影响排序。

## 3. 构建可重复性

检查：

- 从干净环境能否用文档化命令完成构建。
- 工具链、运行时、系统包和依赖是否锁定到可重现版本。
- 构建是否依赖开发者机器、未声明文件、网络最新版本或人工步骤。
- 生成代码、资产和数据库客户端是否可确定重建。
- 同一源码是否产出可追踪、签名或至少带来源信息的制品。
- 多模块构建是否有正确增量边界，还是任意改动触发全量。

不要在体检过程中擅自升级依赖来“让构建通过”；先记录基线和兼容要求。

## 4. CI 质量门

检查流水线是否：

- 对每个变更运行必要的构建、测试、lint、类型和安全检查
- 保护默认分支并阻止跳过关键门禁
- 区分基础设施故障、flaky 与真实失败
- 对缓存、并行和增量做正确失效
- 使用最小权限、固定 action/plugin 版本并保护 secret
- 保存可诊断的日志、测试报告和制品来源
- 对迁移、部署和回滚脚本做预演

过慢流水线和经常被绕过的门禁是治理风险；“门禁很多”不等于有效。

## 5. 发布与回滚

检查：

- 发布单元、版本规则、变更记录和制品晋级是否明确。
- 环境差异是否由声明式配置表达，还是靠人工记忆。
- 是否支持小批量、金丝雀、蓝绿、feature flag 或其他适合系统的渐进放量。
- 应用回滚是否与数据库/消息 schema 兼容。
- 回滚触发指标、决策人、最大容忍时间和演练记录。
- 紧急修复能否快速发布且不会绕过审计与验证。
- 移动端、桌面端、边缘设备等不可强制升级客户端是否有更长兼容策略。

## 6. 依赖与供应链

检查：

- 直接和传递依赖清单、锁文件、来源和许可。
- 已停止维护、停止支持或含已知漏洞的运行时/库。
- 重复库、冲突版本、私有 fork 和未记录补丁。
- 安装脚本、构建插件、容器基础镜像和外部下载的可信度。
- SBOM、漏洞扫描、secret 扫描和依赖更新机制是否与风险匹配。
- 升级测试是否覆盖行为、性能、数据格式和部署环境。

高危漏洞与停止支持通常优先，但仍要评估升级的行为兼容和回滚。

## 7. 开发者工作流

检查：

- 新环境从零到运行/测试所需步骤和时间。
- 本地依赖是否可替代或有安全的开发环境。
- 常用命令是否统一，错误信息是否可操作。
- 代码生成、格式化、lint 和迁移是否在本地与 CI 一致。
- 单仓/多仓依赖变化是否有协调机制。
- 调试关键路径是否需要生产数据或特殊个人知识。

## 8. 证据与结论

至少运行项目已有的代表性命令，并记录：

- 命令和环境
- 成功/失败、耗时与失败摘要
- 是否是基线已有失败
- 覆盖的层级和未覆盖风险

如果因依赖、权限或环境无法运行，标明“未验证”，不要把静态阅读推断写成测试结论。
