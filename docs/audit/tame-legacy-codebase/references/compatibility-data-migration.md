# 兼容与数据迁移手册

所有破坏性契约和持久数据变化采用“扩展—迁移—收缩”。把代码发布、schema 变化、数据回填、消费者迁移和旧路径删除视为不同步骤。

## 1. 兼容范围

逐项确认：

- 源代码兼容、二进制兼容
- 请求兼容、响应兼容、错误语义兼容
- 事件生产者/消费者兼容
- 新代码读旧数据、旧代码读新数据
- 滚动部署期间新旧实例互操作
- 配置、命令行、文件和缓存格式
- 性能、顺序、时效、权限和副作用等行为兼容
- 备份与恢复版本兼容

兼容可能是方向性的。新服务能读旧数据，不代表旧服务能读新写入。

## 2. 兼容矩阵

为每个变更填表：

| 生产者/存储 | 旧消费者 N-2 | 当前 N-1 | 新 N | 回滚版本 |
| --- | --- | --- | --- | --- |
| 旧契约 | 必须/不必 |  |  |  |
| 扩展契约 |  |  |  |  |
| 新契约 |  |  |  |  |

同时记录：

- 支持窗口及最晚退场日期
- 真实用量和未知消费者
- 契约测试位置
- 负责人和通知渠道
- 允许差异

移动端、桌面端、离线设备和外部合作方通常需要比服务端滚动部署更长的窗口。

## 3. 扩展—迁移—收缩

### Expand

- 新增可空列、表、字段、端点或事件版本。
- 新代码同时理解旧/新形态。
- 保持旧写入和旧读取有效。
- 增加差异、用量和迁移进度遥测。
- 部署并验证回滚版本仍可运行。

避免在此阶段重命名、删除、收紧约束或改变既有字段语义。

### Migrate

- 迁移生产者写入，必要时在单一权威入口适配。
- 可重复、限速、断点续跑地回填历史数据。
- 用影子读、校验查询或平行运行比较。
- 分批迁消费者，监测旧契约用量。
- 处理异常数据并保留裁决记录。

### Contract

- 证明旧消费者、旧写入和回滚窗口已结束。
- 先停止旧写入，再停止旧读取。
- 移除双写、兼容分支和迁移权限。
- 最后删除旧字段/表/端点并归档必要数据。

收缩必须是独立发布，不与新功能或下一轮迁移混合。

## 4. 数据迁移状态机

使用明确状态：

1. Planned：schema、容量、备份、对账和回滚经过评审。
2. Expanded：新结构已部署，旧版本仍兼容。
3. Backfilling：历史数据分批迁移，可暂停和续跑。
4. Shadowing：新读/计算与旧权威结果比较。
5. Dual-compatible：所有受支持版本均可运行。
6. Cutover-canary：少量租户/分片/流量使用新权威。
7. Cutover-complete：新路径权威，旧路径只用于回滚。
8. Observing：稳定窗口和对账持续满足。
9. Contracted：旧结构和权限已移除。

为每个状态定义进入条件、退出条件、监测、最大停留时间和回退边。

## 5. 迁移技术选择

### 离线迁移

适合可接受停机、数据量可控且业务能冻结写入。优点是单一时间点与简单一致性；仍需演练时长、恢复和失败回切。

### 在线回填 + 变更捕获

适合低停机。先快照/回填，再通过日志、CDC 或事件追平增量。明确顺序、删除、重复、断点和最终一致点。

### 应用层双写

仅在没有更可靠的单写+传播方案时使用。必须定义：

- 哪一侧是权威
- 两次写入的顺序和部分失败处理
- 幂等键、重试、补偿和告警
- 定期对账与自动修复
- 最大双写期限和删除负责人

普通的“先写 A 再写 B”无法提供跨存储原子性。

### Outbox/Inbox

适合数据库状态与消息发布一致性。事务内写业务数据和 outbox，异步发布；消费者用 inbox/幂等处理。仍需积压、重复、顺序和清理策略。

### 双读或读修复

适合逐步过渡，但可能放大负载并隐藏数据分叉。记录命中来源和差异，不要永久静默 fallback。

### 影子计算

适合新规则/模型比较。屏蔽外部副作用，对时间、随机、排序等非确定字段做语义归一。

## 6. 对账与验证

至少分四层：

- 结构：schema、类型、约束、索引和权限
- 数量：总数、分区数、空值、重复和孤儿
- 内容：校验和、关键字段和抽样全记录
- 业务：金额守恒、状态合法、引用与聚合结果

对账应：

- 可重复运行并输出确定结果
- 按租户/分片/时间定位差异
- 设允许差异和人工裁决流程
- 覆盖更新、删除、重放和迟到数据
- 在切换前后和稳定窗口持续运行

只比较总行数不足以证明正确。

## 7. 回滚与恢复

区分：

- 代码回滚：旧版本能否理解新 schema/数据
- 路由回滚：流量能否切回旧权威
- 数据回滚：是否逆变换、恢复备份或正向修复
- 业务补偿：已发生外部副作用如何纠正

迁移前要求：

- 经过验证的备份与恢复时长
- 回滚触发阈值和决策权限
- 切换点后产生的新写入如何保留
- 回滚演练或至少在等价环境预演
- 不可逆步骤的明确授权

如果数据已由新模型写入且旧模型无法表达，简单部署旧代码不是有效回滚。

## 8. 收缩与退场

删除旧形态前必须满足：

- 所有已知消费者迁移完成
- 遥测证明旧用量在约定窗口为零
- 未知消费者风险已处理
- 最低支持版本与回滚窗口已结束
- 对账和业务指标连续满足
- 归档、保留、审计和合规义务完成
- runbook、告警、权限和复制任务已更新

收缩后验证旧写入不能悄悄恢复，避免“僵尸兼容路径”。

## 9. 高危反模式

- 同一次发布添加新列并删除旧列
- 先全量回填，再发现转换不是幂等
- 双写无权威源，双方互相覆盖
- 用 fallback 隐藏差异且不监测
- 只用生产全量首次验证迁移脚本
- 回滚只考虑应用，不考虑新写入的数据
- 增加非空/唯一约束前不分析历史脏数据
- 旧客户端不可强制升级却直接改变响应语义
- 永久保留“临时”同步任务和迁移权限

出现不可解释差异、业务不变量破坏、回填落后扩大或恢复时间超预算时，暂停进入下一状态。
