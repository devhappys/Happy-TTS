# 架构与领域模型检查标准

围绕业务能力、依赖方向、数据所有权和可独立变化性检查架构。不要从目录名或架构图直接推断真实边界。

## 目录

1. 现状地图
2. 模块边界与依赖方向
3. 领域模型
4. 数据所有权与一致性
5. 集成与契约
6. 质量属性与适配度
7. 重新划界候选信号

## 1. 先画现状地图

至少识别：

- 用户或上游系统触发的关键业务场景
- 进程、服务、作业、函数、客户端和部署单元
- 同步 API、异步事件、共享文件和数据库连接
- 数据库、表/集合、缓存、搜索索引、对象存储和第三方系统
- 入口、鉴权点、事务边界、失败边界与所有者
- 发布顺序和必须一起部署的组件

用一个关键场景和一个失败场景穿透地图。标记“文档声称的边界”与“代码证明的边界”的差异。

## 2. 模块边界与依赖方向

检查：

- 业务策略能否独立于 UI、框架、数据库和消息中间件理解与测试。
- 依赖是否朝向稳定、抽象和业务核心，还是核心反向依赖外层细节。
- 模块是否只能通过明确契约交互，还是可跨边界访问内部对象或表。
- 是否存在循环、共享全局模块、巨型公共库、公共数据库 schema。
- 一个组件是否能独立构建、测试、部署和回滚；如果不能，原因是什么。
- “分层架构”是否只是文件夹分层，运行时仍由任意层相互调用。
- 插件或扩展机制是否有隔离、版本和失败策略。

典型结构风险：

- 大泥球：边界不稳定，任何地方都可依赖任何地方
- 分布式单体：服务很多，但必须锁步修改、测试和发布
- 纳米服务：通信和运维成本高于业务隔离收益
- 共享内核失控：公共包承载不断增长的业务语义
- 中心协调者：单个 orchestrator 知道所有细节并成为瓶颈
- 层层转发：controller/service/repository 只做机械透传

## 3. 领域模型

检查：

- 代码语言是否与业务人员使用的语言一致；同一词是否在上下文中有不同含义。
- 领域不变量位于哪个边界，由谁保证，数据库约束是否与之冲突。
- 实体、值对象、策略、状态机和领域服务是否表达真实规则。
- 领域对象是否只是 getter/setter 容器，规则散落在流程脚本中。
- 一个模型是否试图覆盖互相冲突的上下文。
- 聚合或事务边界是否过大，造成锁竞争和无关耦合；是否过小，无法保证不变量。
- 跨上下文翻译是否通过明确适配/防腐层，还是直接共享内部枚举和表结构。
- 报表/查询模型是否被强迫与写入模型完全一致。

领域重塑的证据应来自业务能力、规则冲突、变化模式和数据所有权，不应仅来自实体表数量。

## 4. 数据所有权与一致性

检查：

- 每类事实是否有唯一权威来源和明确写入者。
- 多个服务是否直接写同一表；是否绕过拥有者的规则。
- 跨模块事务是业务必需，还是边界错误的结果。
- 最终一致性是否定义延迟、冲突、重复、乱序和补偿语义。
- 事件是领域事实还是内部数据快照；消费者是否依赖生产者私有字段。
- 物化视图、缓存和索引能否重建，重建期间如何服务。
- 数据模型是否因历史兼容而包含多套互相矛盾的状态表达。

## 5. 集成与契约

检查：

- API 或事件是否围绕稳定业务能力，而不是暴露内部数据库结构。
- 超时、重试、幂等、限流、背压、熔断和降级责任是否清晰。
- 同步调用链是否过深；一次请求是否跨越过多故障域。
- 消息顺序、去重、重放、死信和 schema 演进是否定义。
- 第三方系统是否被适配层隔离；供应商概念是否渗透核心模型。
- 批处理和在线路径是否对同一规则给出不同结果。

## 6. 质量属性与适配度

不要评价“架构是否先进”，而要评价其是否满足明确质量属性：

- 可修改性：一个典型变化需要多少边界和团队协同
- 可测试性：关键规则能否快速、确定地验证
- 可靠性：故障是否隔离，恢复是否有界
- 性能与伸缩：瓶颈是否可测，状态是否限制水平扩展
- 安全与合规：信任边界和数据分类是否可执行
- 可部署性：发布、回滚和兼容窗口是否独立
- 可观测性：跨边界行为是否可关联和解释
- 成本：运行、许可、开发和认知成本是否匹配价值

把每个目标写成可验证的适配函数，例如“模块 A 不得导入模块 B 的基础设施包”“旧客户端在两个版本窗口内仍通过契约测试”。

## 7. 重新划界的候选信号

提高深度现代化优先级的组合证据：

- 业务能力变化频繁且每次跨越同一组错误边界
- 规则在多个渠道/服务重复且持续分叉
- 数据无单一所有者，事故反复来自跨模块写入
- 发布必须锁步，团队无法独立交付
- 当前模型无法表达关键不变量，补丁主要靠条件分支叠加
- 核心技术或运行环境已停止支持，无法安全维护
- 目标业务模式与当前架构的成本曲线根本冲突

降低深度改造优先级的信号：

- 系统稳定、变化少、事故成本低
- 缺陷集中在少数可隔离组件
- 缺少业务专家或规则来源，重建会丢失隐含知识
- 无可靠数据迁移、并行验证或回滚路径
- 团队无法承担新架构的运维复杂度

是否进入 G3/G4 使用 deep-modernization.md 的决策门，不要凭单一架构味道决定。
