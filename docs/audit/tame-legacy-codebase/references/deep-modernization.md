# 深度现代化、重建与退役决策

G3/G4 不是“更彻底所以更好”，而是高成本投资选择。只有局部治理无法满足明确业务目标且迁移风险可管理时推荐。

## 1. 先定义目标

把“代码太烂”翻译成可验证结果：

- 关键功能交付周期从什么水平改善到什么水平
- 哪类事故、数据错误或安全暴露必须降低
- 哪个成本曲线、容量或延迟目标无法由现状满足
- 哪个停止支持日期或监管期限必须处理
- 哪些业务能力需要独立变化、部署或扩缩
- 哪些隐含规则必须保留，哪些历史行为允许纠正

没有可衡量目标时，只推荐 G1/G2 的可逆改进。

## 2. 六类路线

| 路线 | 适用信号 | 主要风险 |
| --- | --- | --- |
| 保留 | 稳定、低变化、低风险，改造收益不足 | 技术停止支持或人才流失被忽略 |
| 止血 | 问题集中、需要快速降险 | 根因仍在，债务继续累积 |
| 渐进重构 | 业务持续变化，可制造接缝 | 临时双轨持续太久 |
| 重新架构 | 边界/数据所有权根本错误，质量属性不达标 | 分布式复杂度、迁移成本 |
| 重建/替换 | 核心价值低或技术不可救，需求与数据可重建 | 隐含规则丢失、切换集中 |
| 退役 | 价值低、重复或无真实使用 | 未知消费者和保留义务 |

可借鉴“R 类”思路，但按本项目能力逐项选择，不要求整套系统只选一个路线。

## 3. 深改决策门

进入 G3 至少同时满足：

- 有明确业务/质量目标，且 G2 无法经济地达到。
- 根因证据指向领域边界、数据所有权或部署/故障边界。
- 有业务专家和真实规则来源参与。
- 有阶段性交付方案，不需长时间冻结现有产品。
- 兼容、数据、观测和回滚路线可行。
- 团队具备目标架构的建设与长期运维能力。
- 目标方案的复杂度预算明确。

任一关键项未知时，先安排探索切片：建立系统地图、抽取一个模块、回放一段流量或试迁一小类数据。

## 4. 领域与目标架构

采用以下顺序：

1. 识别关键业务能力、参与者、命令、事件和不变量。
2. 区分核心、支撑和通用能力；不要对所有区域投入相同设计。
3. 发现词义冲突和不同变化节奏，提出候选限界上下文。
4. 为每个上下文指定数据权威源、写入者和公开契约。
5. 选择交互方式：进程内模块、同步 API、事件或批处理。
6. 用质量属性场景验证边界，不从数据库表一比一拆服务。
7. 先在模块化单体或防腐层中验证边界，再决定独立部署。

目标架构必须说明：

- 为什么比现状更能满足目标
- 新增了哪些运行与认知成本
- 哪些适配函数持续保护依赖方向、契约和数据所有权
- 最小可行平台能力和团队责任

## 5. 重建门禁

只有以下组合证据足够强时考虑 G4 重建/替换：

- 可保留的业务知识已被可靠提取为规则、样例、契约和数据不变量。
- 当前实现的高价值代码比例低，复用成本高于重建。
- 新旧可按能力、租户、渠道或时间窗口并行。
- 数据可重复迁移并可对账；无法对账的差异有业务裁决方式。
- 新系统在达到业务等价前不宣告完成。
- 有明确预算、所有者、切换日期和旧系统退役计划。

反对大爆炸重写的信号：

- 需求仍快速变化且没有权威来源
- 旧系统包含大量未理解的例外和人工流程
- 新系统只有技术目标，没有业务切片
- 必须一次性迁移所有消费者与数据
- 没有生产影子验证、回滚或双版本运行能力
- 同时更换团队、领域模型、语言、存储和基础设施

## 6. 分阶段路线

推荐阶段：

### A. 探索与基线

- 建地图、契约清单、数据画像和关键场景特征测试
- 定义目标指标、决策日志和退出条件

### B. 建边界

- 引入 facade、防腐层、模块边界和唯一写路径
- 旧行为保持权威

### C. 试点切片

- 选择高价值、低跨域依赖的纵向能力
- 新模型/架构在接缝后实现
- 影子比较与有限放量

### D. 迁移波次

- 按能力迁消费者、数据和运行责任
- 每波都有兼容窗口、对账、回滚和收益复盘

### E. 收缩

- 旧流量为零且稳定窗口满足后删除旧路径
- 归还权限、停止复制、归档数据、更新 runbook

每阶段都能选择继续、暂停、回滚或改变目标，不以“已经投入很多”为理由继续错误路线。

## 7. 停止与转向条件

预先定义：

- 差异率或关键不变量超过阈值
- 数据迁移无法在窗口内完成或回滚
- 新架构运行成本/延迟超过预算
- 团队交付速度没有在试点改善
- 业务目标或监管期限改变
- 关键专家/依赖不可用
- 临时双轨超过最大期限

停止不等于失败；可以退回模块化、保留或替换局部能力。报告应说明沉没成本和可复用成果，但决策只看未来收益与风险。
