# 代码清理手册

在 SKILL.md 选定的 G/Q/C/D 边界内清理。清理的目标是减少理解成本、变更扩散和错误机会，不是追求最少行数或统一个人风格。

## 目录

1. 检查顺序
2. 代码行数与形状
3. 可读性
4. 可维护性
5. 逻辑正确性与文档契约
6. 术语、版本与 legacy 命名沉积
7. 死代码与安全删除证明
8. 按清理深度实施
9. 验证与收尾

## 1. 检查顺序

按以下顺序工作：

1. 建立第一方代码量、最长文件/符号和目录分布。
2. 阅读最大单元、变化热点、关键路径和缺陷集中区。
3. 检查可读性，再检查职责、依赖和变更成本。
4. 对照文档、测试和调用者验证逻辑，而非默认现有行为正确。
5. 盘点重复、死代码、废弃依赖、配置分叉和命名沉积。
6. 逐项写入发现账本，再按 Q 档实施。

完成扫描后，账本应覆盖声明范围内所有已确认问题和仍需裁决的候选；不得只保留“大问题”。

## 2. 代码行数与形状

代码行数是首要导航指标。至少记录：

- 第一方生产代码、测试代码、生成/供应商代码的文件数与物理行数；配置、迁移和文档单列。
- 按物理行数排序的最长文件，以及工具可可靠识别时的最长函数、方法、类型和模块。
- 行数在目录/模块间的分布；少数文件是否承载大部分实现。
- 大文件是否同时具有高变化频率、缺陷历史、低测试覆盖、跨层依赖或多个变化原因。
- 清理前后行数变化，并解释新增测试、类型或文档导致的合理增长。

优先使用仓库已有的 `scc`、`tokei`、`cloc` 或语言工具；否则运行 `scripts/inventory_codebase.py`。采用 Git 跟踪文件优先，排除生成物、供应商代码、构建输出和本次报告。

物理行数包含空行和注释时明确说明。阈值用于排序而非定罪：高度内聚的解析器、协议表、迁移或生成文件可以很长；短文件也可能通过全局状态和隐式依赖制造高维护成本。

把“行数大”升级为问题前，至少连接到以下一项：

- 无法用一句话描述单一职责。
- 普通改动需要在文件内跨越无关区域。
- 控制流、状态或副作用难以局部推理。
- 多个团队/功能频繁冲突或共同修改。
- 测试只能通过昂贵的整体装配运行。
- 缺陷、性能或安全问题集中出现。

## 3. 可读性

检查并记录：

- 命名能否表达领域概念、单位、状态和副作用。
- 深层嵌套、过长条件、布尔开关、隐式 fall-through 和非局部跳转。
- 函数签名是否暴露必要输入输出，还是依赖全局状态、环境或调用顺序。
- 注释是否解释约束与原因，是否与实现漂移，是否用大段叙述掩盖难懂代码。
- 魔法数字、字符串协议、单位/时区/精度和未知默认值。
- 异常与返回值是否让成功、业务拒绝和程序缺陷可区分。

清理优先采用局部、行为保持的动作：具名中间量、早返回、提取纯计算、缩小状态作用域、明确类型和错误。避免为减少行数压缩表达式，也避免为了“整洁”拆出只增加跳转层数的薄包装。

## 4. 可维护性

检查并记录：

- 一个典型变化触及的文件、模块、契约和团队数量。
- 业务规则是否有单一权威实现，复制版本是否已经分叉。
- 核心策略是否依赖框架、数据库、网络、全局单例或内部表结构。
- 模块是否内聚，依赖是否单向，公共 util/helper/common 是否成为无边界容器。
- 测试是否保护业务结果，还是紧贴实现细节而阻止安全重构。
- 临时 flag、兼容层、适配器、迁移脚本和例外是否有所有者与退场条件。
- 依赖、运行时和自定义框架是否仍受支持，能否安全升级或移除。

重复两次不自动要求抽象；先判断它们是否代表同一规则、是否会同步变化。抽象必须减少真实变化成本，而非只降低表面行数。

## 5. 逻辑正确性与文档契约

代码清理必须主动寻找逻辑 bug。重点验证：

- 空值、边界、默认值、排序、分页、去重、时区、金额、精度和编码。
- 状态转换、权限、计费、库存、配额、重试、幂等和部分失败。
- 异常、提前返回和取消是否跳过清理、补偿或资源释放。
- 同一规则在入口、服务、数据库、前端、批处理和文档中是否矛盾。

在修改前建立“功能标准清单”：

- 收集 README、产品说明、ADR、API/schema、CLI 帮助、示例、测试名与断言。
- 标出每个功能的权威来源、消费者和证据强弱。
- 文档列出但代码似乎未使用的功能不得直接删除；先判断实现缺失、文档过期、隐藏入口或兼容承诺。
- 文档与代码冲突且仓库证据无法决定权威时，创建 `Suspected` 发现并询问用户。
- 仓库没有解释用途、关键流程、内部术语或运行方式的文档时，创建 Info 发现；不要把缺文档误写成代码 bug。

修复确认的 bug 时先增加能暴露错误的回归测试。完成后把正确行为反哺到相应文档、示例、帮助文本和术语表；若没有合适文档，记录建议的最小文档位置。

## 6. 术语、版本与 legacy 命名沉积

主动搜索以下可读性噪音：

- 没有词汇表或上下文解释的内部简称、阶段名和编号，如 `M3`。
- 只有 `v2`/`V2`，却没有并存 `v1`、版本协商、迁移窗口或外部版本契约。
- `legacy`、`old`、`new`、`tmp`、`temp`、`final` 等已经不再区分真实并存概念的名称。
- 名称与目录、文档、日志、指标和配置使用不同术语表示同一概念。

逐个候选执行：

1. 搜索声明、静态引用、字符串引用、配置、脚本、序列化、遥测、文档和测试。
2. 判断名称是否出现在公开 API、CLI、事件、存储格式、插件反射、动态加载或外部自动化中。
3. 查看历史或迁移说明，确认后缀是否仍表达兼容窗口或业务阶段。
4. 能证明是纯内部、无语义且替代名明确时，原子重命名所有引用并更新文档。
5. 名称噪音可确认、替代语义却不明确时，记录 Info；是否承载功能/兼容语义不明时，记录 `Suspected` 并询问用户。

每个需要不同解释、消费者证明或删除决策的候选都单独记账；不能把 `M3`、孤立 `route_v2` 和 `legacy_dispatch` 合并成一个泛化的“缺文档”发现。重复的同类名称可以共用一个发现，但必须完整列出所有位置。孤立版本后缀若可能属于公开符号或外部契约，必须作为独立 `Suspected` 询问；只有证明为纯内部且没有并存版本语义后，才按所选 Q 档删除后缀。

“删除 legacy 噪音”通常是删除无意义的词和分支，不等于删除它所指向的功能。仍与新路径并存、承担回滚或服务旧消费者的 `legacy` 是有效区分，直到退场条件满足。

## 7. 死代码与安全删除证明

删除代码、依赖、配置或文档前组合验证：

- 静态引用、调用图和构建入口均无消费者。
- 动态加载、反射、插件、路由、任务调度、模板、脚本和运维入口已检查。
- 公开契约、遥测、发布清单和支持版本没有用量或承诺。
- 文档、测试、示例与历史迁移没有声明仍支持该能力。
- 删除后构建、测试、打包和代表性运行路径通过。
- 高风险路径有可回滚变更或明确恢复方式。

证据不足时保留代码，把缺失的用量证明写成 `Suspected` 问题。静态“无引用”只能证明一种引用方式没有出现。

## 8. 按清理深度实施

Q0 只维护报告和证据。

Q1 适合：

- 未使用导入、局部不可达代码和已证实无引用的私有成员。
- 过期注释、拼写、明确命名噪音和小范围控制流简化。
- 一个已确认逻辑 bug 及其回归测试。
- 与当前改动直接相关的文档同步。

Q2 在 Q1 之外适合：

- 拆分职责混杂的长文件/长函数并建立行为安全网。
- 收敛已分叉的同一业务规则，删除完整列出的重复实现。
- 清理范围内所有已证实死代码、废弃依赖、过期 flag 和配置分叉。
- 建立必要的边界测试、契约测试和最小术语/功能文档。

Q3 才处理：

- 跨模块清除整套旧实现、兼容垫片和迁移基础设施。
- 全仓统一仍广泛存在的版本/legacy 命名。
- 删除需要运行遥测、消费者迁移或退场窗口证明的路径。

每个 Q 档都允许发现更深问题；超过授权档位的项留在报告，不顺手扩大实施。

## 9. 验证与收尾

至少完成：

- 对每个已改发现运行最接近失败模式的验证。
- 运行受影响范围的项目原生格式、lint、类型检查、构建和测试。
- 对比清理前后第一方物理行数、最大单元、依赖与测试变化，解释差异而非追求单向下降。
- 搜索旧名称和旧入口，确认应删除的引用归零、应保留的契约仍存在。
- 检查文档、帮助、示例和代码术语一致。
- 在报告中更新每个发现的处置状态与验证证据，并保留未处理项。

验证失败时回到对应发现，不把部分通过写成完成。
