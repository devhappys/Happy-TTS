# 文档、所有权与团队演进检查标准

软件结构和交付组织共同决定可维护性。只改代码、不修复知识和责任断点，技术债会重新长回来。

## 1. 知识与文档

检查：

- 仓库是否至少存在解释项目用途、用户入口、关键功能和运行方式的文档；缺失时建立 Info 发现。
- 项目目的、边界、关键业务词汇和不变量是否可找到。
- `M3`、内部阶段编号、缩写、孤立版本后缀和 `legacy` 等术语是否有词汇表或上下文定义。
- 从零构建、运行、测试、发布和回滚是否有可执行说明。
- 架构图是否标注日期、范围和事实来源；是否与代码/部署一致。
- 关键决策是否记录背景、备选项、取舍和失效条件。
- API、事件、数据字典和配置是否有权威来源。
- runbook 是否包含诊断、止血、恢复、升级和验证步骤。
- 文档是否有所有者和更新触发点，而非一次性补写。

把可由代码、schema 或命令自动生成的事实自动化；文档重点解释意图、约束和例外。

审计和清理前，先把文档、示例、CLI 帮助、schema 与测试中列出的功能整理成“功能标准清单”。文档可能过期，但在权威性查清前仍是契约证据：不能仅凭静态无引用就删除其中声明的功能。代码与文档冲突且无法由仓库证据裁决时，记录为 Suspected 并询问用户。

代码修改后反向检查文档：行为、接口、术语、命令、架构、部署或恢复方式发生变化时，在同一工作中更新对应权威文档。没有合适文档承载变化时，记录缺口和建议位置，而不是让代码与说明继续分叉。

## 2. 所有权

检查：

- 模块、数据、服务、依赖和线上告警是否有明确负责方。
- 所有者是否有修改、发布和恢复所需权限及知识。
- 关键组件是否只有一个人能处理；休假或离职时会怎样。
- 跨团队契约由谁批准、通知、监测和退场。
- 公共模块是否因“人人负责”而实际无人负责。
- 维护责任是否与业务价值和运行风险匹配。

## 3. 变化流

选取近期需求、缺陷和事故，检查：

- 从理解到上线的等待点和交接次数
- 变更跨越多少仓库、模块、团队和发布窗口
- 审查是否能由熟悉上下文的人完成
- 是否存在大批量合并、长期分支和痛苦集成
- 是否因环境、数据、权限或测试不稳定而反复返工
- 紧急发布是否绕过正常质量门

高变更耦合和组织耦合是架构边界候选证据，但不能仅凭团队图设计服务。

## 4. 代码审查与工程规则

检查：

- 审查是否关注行为、风险、契约和可运维性，而不只是格式。
- 大变更是否拆成可理解、可回滚的切片。
- 自动化规则是否与人工审查分工，减少噪声。
- 例外是否记录期限和所有者。
- 依赖、schema、权限和基础设施变更是否有相应专家审查。
- 技术债是否有进入、排序、偿还和关闭的统一标准。

## 5. 历史与热点

在历史可用时，组合观察：

- 高频变化文件/模块
- 缺陷和事故集中区域
- 多人反复冲突区域
- 频繁一起变化却位于不同边界的文件
- 长期无人触碰但业务关键的“冻结核心”

历史热点帮助决定先读哪里，不代表频繁变化本身是坏事。业务价值高的核心自然会更活跃。

## 6. 认知负担与平台依赖

检查：

- 完成普通需求需要理解多少无关框架和基础设施细节。
- 本地开发是否必须手工启动大量服务。
- 平台能力是否自助、可发现、有稳定契约。
- 自定义框架、内部 DSL 和脚手架是否有维护者和退出路径。
- 团队是否具备目标架构所需的运行、数据和安全能力。
- 新技术是否减少整体复杂度，还是把代码复杂度转成平台复杂度。

## 7. 治理可持续性

建议为重复出现的根因建立：

- 架构适配函数和依赖边界测试
- 契约兼容门禁
- 依赖和运行时支持期限
- 技术债预算或固定偿还节奏
- 事故复盘到代码/流程改进的闭环
- 兼容垫片和 feature flag 的退场清单
- 可度量的开发反馈时间与发布健康指标

不要用统一大规范压制局部自治。规则应保护明确的不变量和边界，并允许团队在边界内选择实现。
