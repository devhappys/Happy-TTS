# 渐进治理方法手册

把改造拆成持续可发布、可比较、可回滚的切片。根据问题位置选择技术，不套用单一模式。

## 1. 治理顺序

优先顺序通常是：

1. 控制正在发生的安全、数据或可用性损失。
2. 恢复可构建、可测试、可发布和可回滚。
3. 增加关键路径的可观测性与行为基线。
4. 隔离变化热点和外部依赖。
5. 修复边界、所有权和模型。
6. 最后删除旧路径、兼容层和临时开关。

不要把目录整理、统一格式、全量重命名当作第一阶段；它们会制造噪声并干扰历史追踪。

## 2. 建立安全网

没有可靠单元测试时，先选择最低成本的行为捕获：

- 特征测试：固定现有输入输出，包括已知怪异行为；先保护再决定是否纠正。
- 黄金主流程：从稳定入口覆盖最重要的端到端业务结果。
- 契约测试：冻结公开 API、事件、序列化和旧版本交互。
- 黄金文件/快照：适合复杂文本、协议或序列化，但审查差异语义。
- 数据不变量测试：金额守恒、引用完整、状态合法、行数与校验和。
- 记录回放/影子执行：对同一真实形状输入比较新旧实现，不产生副作用。

先覆盖将要切开的接缝和最大损失路径，不追求全仓库覆盖率。

## 3. 制造接缝

接缝是无需在调用处修改即可替换行为的位置。可用方法：

- 把时间、随机、文件、数据库、网络和全局配置包进窄适配器。
- 在巨型函数中先抽取无副作用计算，再隔离 I/O。
- 引入 facade 统一多个不稳定入口。
- 用防腐层把第三方或旧模型翻译成内部语言。
- 在调用点前引入兼容接口，再把旧实现放到接口后。
- 用路由、代理或 feature flag 控制旧/新实现比例。

接缝必须有明确寿命。为了迁移引入的临时抽象在收缩阶段删除，避免永久增加层数。

## 4. 局部设计治理

按小步执行：

1. 写下当前行为和失败边界。
2. 添加最小测试。
3. 做一个行为保持变换。
4. 运行快速验证。
5. 提交/记录一个可解释意图。

常用动作：

- 拆分查询与命令，显式标记副作用。
- 用值对象或类型封装金额、ID、状态、时间和单位。
- 把条件组合提升为具名策略或状态机。
- 把重复业务规则收敛到权威位置；保留仅表面相似的重复。
- 缩小可变状态作用域和资源生命周期。
- 用结构化错误替代吞异常和魔法返回值。
- 反转核心策略对框架/存储细节的依赖。
- 删除有运行证据证明无人使用的死代码。

避免一次性重写整个文件。每步保持编译和测试可通过。

## 5. 模块与领域边界

先在当前部署单元内建立模块化边界：

- 按业务能力聚合代码，而非只按技术层。
- 定义公开入口，隐藏内部类型和表。
- 指定数据所有者和唯一写路径。
- 增加依赖方向测试或架构适配函数。
- 用模块间契约测试保护交互。
- 把跨模块共享模型改为显式翻译。

只有在独立扩缩、独立发布、故障隔离、监管或团队自治带来可证明收益时，才拆为独立服务。模块化单体常是验证边界的低风险中间态。

领域模型重塑顺序：

1. 与业务专家梳理关键场景、事件、命令、规则和冲突词义。
2. 找出稳定不变量与变化率不同的能力。
3. 定义上下文边界、权威数据和翻译关系。
4. 选择一个高价值、边界相对清楚的纵向切片。
5. 在防腐层后实现新模型并与旧模型比较。
6. 按能力迁移消费者和数据。

## 6. 大规模替换模式

### 绞杀榕模式

适合能在系统边缘按能力、路由或租户切分的替换：

1. 在旧系统前建立可观测路由。
2. 新实现先接少量只读或低风险流量。
3. 比较行为与指标。
4. 按能力逐步迁移。
5. 确认旧能力无流量后退役。

不适合无法路由、共享事务强耦合且无数据所有权的核心；先制造边界。

### 分支抽象

适合系统内部耗时较长的实现替换：

1. 在旧实现前引入稳定抽象。
2. 所有调用先走抽象，行为不变。
3. 在抽象后实现新路径。
4. 用开关或配置在同一主干中切换/比较。
5. 完成迁移后删除旧实现和临时抽象。

不要用长期源码分支隐藏大改；持续合入可发布状态。

### 并行变更

适合接口或 schema 的不兼容演进：

1. Expand：只增加新能力，旧消费者仍工作。
2. Migrate：迁移生产者、消费者和数据，观察旧用量归零。
3. Contract：到期后删除旧元素。

详细数据步骤见 compatibility-data-migration.md。

### 平行运行与影子流量

适合高正确性要求：

- 旧路径保持权威，新路径接同形输入但屏蔽副作用。
- 对结果做语义比较，过滤非确定字段。
- 分类差异：旧 bug、新 bug、允许差异、数据时序差异。
- 达到样本、时间和关键不变量阈值后再切权威。

注意隐私、成本和影子路径对下游的意外副作用。

## 7. 依赖与平台升级

升级顺序：

1. 记录运行时、库、插件和行为基线。
2. 读取迁移指南与停止支持风险。
3. 先升级一个兼容跨度或一个依赖簇。
4. 用适配层隔离 API 差异。
5. 运行契约、性能和部署验证。
6. 清理适配层和旧锁定。

框架迁移与领域重构同时进行会扩大差异来源；除非旧框架阻止建立接缝，否则分开切片。

## 8. 清理与防复发

收缩阶段必须：

- 用运行遥测证明旧接口、字段、flag 和路径无消费者。
- 删除旧实现、临时双写、适配器、迁移权限和告警。
- 更新权威文档、所有权和 runbook。
- 增加边界测试、契约规则或 CI 门禁防止回流。
- 比较治理前后的变更范围、失败率、反馈时间和运行指标。
- 关闭对应发现项并记录剩余例外的期限。

## 9. 失败模式

- 大爆炸重写：多年不交付，隐含规则丢失，切换风险集中。
- 永久双轨：新旧都维护，数据分叉，成本翻倍。
- 只搬代码不改所有权：服务拆了但共享表和锁步发布仍在。
- 先做抽象再找问题：产生通用框架和错误统一。
- 用测试固定所有 bug：没有区分兼容行为与应纠正缺陷。
- 指标游戏：为覆盖率或复杂度数字重写低价值稳定代码。
- 清理过早：旧消费者、回滚版本或历史数据仍依赖旧形态。
- 清理永不发生：兼容层和 feature flag 成为下一代屎山。
- 过度并行：同时改领域、框架、存储、协议和部署，无法定位差异。

出现差异无法解释、错误率上升、对账不守恒、回滚未验证或兼容消费者未知时，停止放量并回到上一个稳定阶段。
