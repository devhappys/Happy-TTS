# 性能、可观测性与运维检查标准

性能问题必须由工作负载、服务目标和测量证明。不要从代码形状直接断言瓶颈，也不要在没有基线时优化。

## 1. 服务目标与工作负载

先明确：

- 关键用户旅程及其延迟、吞吐、可用性和正确性目标
- 平均、峰值、突发、批量和灾难恢复工作负载
- 数据规模、增长率、租户倾斜和热点分布
- 可接受的数据陈旧度、排队时间和降级方式
- 当前基线、容量余量和成本约束

如果没有 SLO，至少从业务损失和用户体验定义可验证的预算。平均值不能代表尾延迟。

## 2. 应用路径

检查：

- 算法复杂度是否随真实数据规模恶化。
- 重复计算、无界集合、全量加载、低效序列化和过度复制。
- N+1 调用、同步串行 I/O、深调用链和聊天式远程接口。
- 缓存命中率、key 基数、TTL、击穿、雪崩、污染和失效成本。
- 批处理大小、流式处理、分页和背压是否有界。
- 日志、追踪和指标是否在热路径产生显著开销。
- 内存保留、GC 压力、线程/协程池、连接池和文件描述符。

先用 profiler、trace、查询计划或计数器定位时间和分配，不凭直觉重写。

## 3. 数据库与存储

检查：

- 关键查询计划、扫描行数、索引选择、排序和临时空间。
- 索引是否支持真实过滤/连接，还是重复或拖慢写入。
- 事务过长、锁等待、热点行、连接耗尽和隔离级别成本。
- ORM 是否隐藏 N+1、过量列、意外级联或逐行更新。
- 分页是否在深页退化；游标稳定性是否满足业务语义。
- 读副本、缓存和搜索索引的一致性与路由。
- 大表 schema 变更、回填和索引创建的在线影响。

优化前保存可复现查询、参数分布、计划和基线；优化后验证正确性而不只看耗时。

## 4. 网络与分布式路径

检查：

- 请求次数、payload 大小、压缩、序列化和连接复用。
- 跨区域/跨可用区/跨供应商调用与数据传输成本。
- fan-out 数量及最慢依赖对尾延迟的放大。
- 超时预算是否沿调用链递减；重试是否放大流量。
- 批量接口和异步化是否真正降低关键路径，还是延后不可见故障。
- CDN、边缘缓存和客户端缓存的版本/失效语义。

## 5. 容量与稳定性

检查：

- 资源限制与请求、自动扩缩阈值和冷启动。
- 队列容量、积压恢复速度和生产/消费速率。
- 负载升高时系统是优雅降级还是骤然崩溃。
- 单租户或单 key 是否能耗尽共享资源。
- 容量模型是否包含故障转移、回填、重放和发布期间的额外负载。
- 压测是否使用现实分布、缓存状态、数据量和依赖行为。

## 6. 可观测性

检查：

- 指标、日志、追踪是否覆盖关键业务结果和技术资源。
- 是否能用关联 id 贯穿同步、异步和批处理路径。
- 高基数标签、敏感字段、采样和保留策略是否安全且可负担。
- 错误率是否区分业务拒绝、客户端错误、依赖故障和程序缺陷。
- dashboard 是否围绕服务目标、饱和度和用户影响。
- 告警是否可操作，有所有者、阈值依据、抑制和 runbook。
- 部署版本、feature flag、租户和依赖变化能否与回归关联。

日志很多但无法回答“谁受影响、从何时开始、由哪个版本导致”仍属于不可观测。

## 7. 运维准备度

检查：

- 健康检查是否反映服务能力，避免过深依赖造成级联重启。
- 启动、优雅关闭、连接排空和作业接管。
- 配置发布、secret 轮换、证书到期和时间同步。
- 备份、恢复、扩容、降级、切流和事故处置 runbook。
- 管理操作是否可审计、幂等并支持 dry-run。
- 定时任务、数据修复和一次性脚本是否纳入版本和审查。
- 资源所有者、值班和升级路径是否明确。

## 8. 成本与效率

检查：

- 成本是否可按服务、租户、功能或环境归因。
- 闲置资源、过度保留、重复存储和高价跨区传输。
- 性能优化是否把成本转移到更复杂运维或更差一致性。
- 新架构的固定平台成本是否适合当前规模。
- 构建、测试和开发环境的等待成本。

不要把最低基础设施账单等同于最低总拥有成本。

## 9. 验证产物

性能发现至少包含：

- 现实工作负载与数据规模
- 测试环境与限制
- 基线分布，而不只是单个平均值
- profiler/trace/query plan 等定位证据
- 优化后的正确性、尾延迟、资源和成本对比
- 回归阈值及持续监测方式

无法复现的生产慢问题应标为待观测，不要用大规模重写代替测量。
