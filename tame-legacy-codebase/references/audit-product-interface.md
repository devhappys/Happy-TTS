# 功能适合性、界面与可访问性检查标准

项目治理不能只改善内部结构。确认系统仍完整、正确、可理解地支持真实用户任务，并且改造不会让旧用户、辅助技术或弱网络环境失效。

## 1. 功能适合性

检查：

- 核心业务场景是否完整，是否存在只能靠人工补偿的断点。
- 实现是否符合当前规则、监管和产品承诺，而不是过期文档。
- 功能输出的精度、时效和边界条件是否满足用途。
- 用户完成任务是否经过无关步骤、重复输入或绕路。
- 同一能力在 Web、移动端、API、批处理和后台工具中是否语义一致。
- 同一任务存在多个入口时，它们是正式用户路径、兼容入口、管理员后门还是历史残留；产品文档和用户心智是否明确。
- 长期无人使用、重复或被替代功能是否有运行证据与退役可能。
- feature flag、地区版和租户定制是否形成不可测试的功能组合。

把缺失功能与内部技术债分开报告；不要借重构偷偷改变产品语义。

例如以 supervisor 编排 Claude Code/Codex 的系统同时保留用户直调 CC/CX 的代码路径，不能仅凭主架构叙述删除直达入口。先检查 UI/CLI、帮助、测试、遥测、兼容承诺与外部调用；仍无法判断时建立 Suspected 发现，把“应保留为正式能力、标记弃用还是删除”连同证据集中询问用户。

## 2. 交互状态与恢复

检查：

- 加载、空数据、部分数据、成功、失败、超时和离线状态是否明确。
- 重复点击、刷新、返回、跨页和多标签操作是否造成重复副作用或丢失输入。
- 长任务是否显示进度、可取消、可恢复并避免假成功。
- 表单验证是否就地、可理解并保留用户输入。
- 破坏性操作是否有适当确认、撤销或恢复路径。
- 会话过期、权限变化和并发编辑是否给出安全反馈。
- 客户端缓存、乐观更新和服务端权威结果冲突时如何收敛。

## 3. 可访问性

对有用户界面的项目检查：

- 键盘可操作、焦点顺序、焦点可见和焦点恢复。
- 语义化结构、可访问名称、标签、标题和地标。
- 屏幕阅读器可理解动态更新、错误和状态变化。
- 颜色不是唯一信息载体；对比度和缩放后内容仍可用。
- 动画、闪烁、超时和拖拽是否有替代或减弱方式。
- 触控目标、响应式布局、横竖屏和文本放大。
- 图像、图表、音视频是否有等价文本或字幕。

优先使用项目现有可访问性测试和人工键盘/辅助技术验证。自动扫描不能证明整体可访问。

## 4. 国际化与内容

检查：

- 文本是否硬编码在业务逻辑中，翻译 key 是否稳定。
- 日期、时区、数字、金额、单位、姓名和地址格式。
- 复数、语序、从右到左布局和文本扩张。
- 排序、搜索、大小写和 Unicode 归一化。
- 错误信息是否可操作且不泄露内部细节。
- 法律、隐私、同意和数据导出文案是否与实际行为一致。

## 5. 客户端与环境兼容

检查：

- 支持的浏览器、操作系统、设备、SDK 和离线客户端版本。
- 渐进增强、弱网、断网、低内存和低性能设备。
- 深链接、URL、书签、文件导入导出和剪贴板格式是否构成持久契约。
- 客户端无法强制升级时，服务端兼容窗口和降级行为。
- UI 自动化是否只覆盖理想环境，忽略真实设备和辅助技术。

## 6. API、CLI 与开发者体验

没有图形界面时也要检查交互能力：

- API/CLI 命名、发现性、错误、帮助、示例和默认值。
- 幂等、分页、异步任务、速率限制和重试是否容易正确使用。
- 安全默认值是否避免用户必须了解内部实现。
- 版本升级是否有迁移提示、弃用警告和机器可读错误。
- 常见操作能否用稳定脚本自动化。

## 7. 验证方法

组合使用：

- 与业务专家核对关键任务和不变量
- 从真实支持工单、行为分析和失败漏斗抽样
- 不同权限、地区、设备和旧版本的场景测试
- 可访问性自动扫描加键盘/屏幕阅读器人工验证
- 弱网、离线、重复提交和会话过期测试
- API/CLI 的新用户可用性与契约测试

涉及真实用户遥测时保护隐私并避免把“使用少”直接解释为“无价值”；可能是入口难找或功能已经坏掉。
