# 遗留代码清理、体检与治理

把“屎山”转化为完整的发现账本、可验证的改动和可回滚的决策。代码量是首要导航指标，其次检查可读性与可维护性；指标负责决定先读哪里，代码和运行证据负责证明问题。

## 不变量

1. **写穿式记录。** 在仓库中维护一个 Markdown 报告；每发现一个问题，先写入报告，再检查下一个无关位置。不得等扫描结束后凭记忆汇总。
2. **完整列举。** 记录范围内发现的全部 Critical、High、Medium、Low 和 Info 项。相同根因可以聚类，但每个不同问题都保留 ID，重复出现位置完整列出。
3. **事实分层。** `Confirmed` 有代码、命令、测试、运行数据或明确契约支持；`Suspected` 仍依赖产品意图、未知消费者、运行证据或用户裁决。不要用置信度替代这两个状态。
4. **保护功能契约。** 先从文档、测试、示例、CLI 帮助、schema 和现有消费者提取功能标准。代码逻辑本身可能有 bug；既不把现状一律冻结为正确行为，也不借清理删除文档列出的功能。
5. **授权后实施。** 检查、解释或方案请求只读；明确要求修复或治理时，才在选定档位内改动。公开契约、真实数据和不可逆操作继续受硬门禁保护。
6. **规模自适应。** 小问题使用紧凑发现项和针对性验证；只有跨模块、契约、数据或系统级问题才展开系统地图、迁移状态机和多路线比较。
7. **文档闭环。** 改动影响行为、接口、术语、命令、架构或运维方式时，同步更新权威文档；仓库缺少必要文档也作为 Info 发现记录。
8. **双快照。** 任何代码修改都保留不可覆盖的 Before 基线，并在完成后记录 After、差值和解释；不得只展示修复后的干净状态。

## 首轮决策

从用户请求和仓库证据推断档位。只有档位会扩大授权、破坏契约或改变产品语义时才追问。把最终选择写在报告顶部，例如 `轻量 / E2 / G1 / Q1 / C1 / D0`。

### 任务规模

- **轻量**：一个明确问题、局部区域，或规模很小且边界单一的完整仓库；不触及公开契约、持久数据或跨系统边界。使用紧凑报告，不强制系统地图、多方案比较或迁移章节。
- **标准**：多个关联模块、入口或质量维度，存在真实的依赖/契约分析，但不涉及系统级迁移。
- **系统**：跨领域/服务/部署边界、数据所有权、外部消费者、迁移、重写或退役；执行完整地图、路线和迁移分析。

选择能覆盖风险的最小任务规模。检查“整个仓库”不自动等于系统级：几十行的单模块仓库仍可走轻量；单个文件若承载外部契约或数据迁移也可能升级。任务规模只控制过程开销，不降低所声明检查范围内的发现完整性。

### 执行节奏

- **E0 只报告**：完成只读检查、问题账本、评分和建议，不修改代码。（审计/检查请求默认）
- **E1 先报告后修复**：完成并冻结修复前报告，在主对话展示严重度、评分、待裁决问题和建议范围；等待用户确认后再进入修复。（标准/系统清理默认）
- **E2 同轮修复**：每项先记录 Before 证据，再实施已授权修复并记录 After；只用于用户明确要求直接处理的轻量任务，或用户明确要求连续执行。

E1 的“等待确认”是真正的阶段边界，不在展示报告后同一轮自动继续修改。E2 仍必须先写发现账本，不能用最终 diff 反推修复前状态。

### 治理与重构范围

- **G0 只体检**：只输出证据、问题、评分和方案。（检查类请求默认）
- **G1 局部修复**：修复逻辑缺陷、构建阻塞和局部设计问题；保持模块与系统边界基本不变。（处理请求默认，直到证据证明需要扩大）
- **G2 渐进重构**：用特征测试、接缝和模块抽取逐步降低耦合；仅在问题确实跨越局部边界或用户明确要求时选择。
- **G3 深度现代化**：重新划分领域、数据所有权或架构，允许大规模内部变化。
- **G4 重建、替换或退役**：新旧并行、能力逐段切换或明确的一次性切换。

### 清理深度

`Q` 控制“处理多少已确认的清理项”，不控制“报告多少问题”。任何 Q 档都必须记录范围内的全部发现。

- **Q0 只盘点**：不执行清理。（检查类请求默认）
- **Q1 定点清理**：只处理用户目标和顺手可证的低风险局部噪音。（轻量处理默认）
- **Q2 彻底清理当前范围**：处理范围内全部可安全验证的清理项，包括补测试、拆分过长单元、收敛重复和修正文档。（明确要求“全面清理”时默认）
- **Q3 深度收缩**：系统删除已证实无消费者的内部旧路径、兼容垫片、配置、依赖和命名沉积；必须获得用户明确授权。

G 与 Q 相互独立：全面清理一个小仓库通常是 `G1/Q2`，而只处理大型重构中的一个明确切片可以是 `G2/Q1`。不要因为 Q2 自动升级到 G2。

### 兼容策略

- **C0 严格兼容**：旧行为、API、协议、配置、存储格式和二进制契约均不得破坏。
- **C1 向后兼容**：旧消费者与旧数据继续可用；新消费者可使用扩展能力。（默认）
- **C2 过渡兼容**：新旧契约并存到有期限的退场条件满足。
- **C3 允许破坏**：通过主版本、迁移窗口或统一切换处理；必须获得用户明确授权。

### 数据策略

- **D0 不改数据**：只读分析或代码结构变化。（无数据需求时默认）
- **D1 原地兼容演进**：只做可回滚的扩展式 schema 变化。
- **D2 可逆迁移**：备份、回填、对账、灰度和回滚均已定义。
- **D3 可重置或不可逆迁移**：仅在用户明确允许丢弃、重建或不可逆转换时采用。

G3、G4、Q3、C2、C3、D2 或 D3 未获相应授权时只能作为方案，不得实施。E0 不得实施；E1 在用户确认修复范围前不得实施。

## 执行步骤

### 1. 建立边界与报告

- 阅读仓库级和目录级代理说明、贡献指南、架构/产品文档、迁移说明、运行手册、测试与示例；检查工作树并保护用户已有改动。
- 确认环境性质，不对生产系统、真实数据库、外部消息、凭据或收费资源试验。
- 选择用户指定的报告路径；未指定时使用仓库根目录 `legacy-codebase-report.md`。已有同名非本次报告时选择新文件，保留原内容。
- 立即创建报告头、严重度计数表、评分占位、Before/After 表和发现账本。使用 [prioritization-and-report.md](references/prioritization-and-report.md) 的轻量或完整模板。
- 运行最小构建、测试和静态检查，记录检查前失败。运行 `scripts/inventory_codebase.py` 或项目原生 LOC 工具，分开记录第一方生产、测试、生成/供应商代码的物理行数和最长文件。

完成条件：报告已存在；范围、排除项、任务规模和 E/G/Q/C/D 已记录；Before 基线与 LOC 证据已落盘且标为冻结。

### 2. 扫描并写穿发现账本

按“代码行数与形状 → 可读性 → 可维护性 → 逻辑正确性与功能契约 → 其他适用质量维度”的顺序检查。长文件和长函数先读，但只有结合职责、耦合、变化或缺陷证据后才定严重度。

每发现一项就分配 `F-001` 形式 ID，记录严重度、`Confirmed/Suspected`、证据位置、影响、建议或待裁决问题，并立即更新严重度计数。低风险与 Info 使用单行紧凑记录；高风险、复杂根因或系统级问题再展开完整字段。不得因为模板成本而漏报小问题。

代码清理必须读取 [cleanup-playbook.md](references/cleanup-playbook.md)。其他维度按需读取：

- 功能适合性、界面与可访问性：[audit-product-interface.md](references/audit-product-interface.md)
- 代码与局部设计：[audit-code-design.md](references/audit-code-design.md)
- 架构与领域模型：[audit-architecture-domain.md](references/audit-architecture-domain.md)
- 数据、API 与兼容契约：[audit-data-contracts.md](references/audit-data-contracts.md)
- 测试、构建、交付与依赖：[audit-tests-delivery.md](references/audit-tests-delivery.md)
- 安全、可靠性与并发：[audit-security-reliability.md](references/audit-security-reliability.md)
- 性能、可观测性与运维：[audit-performance-operations.md](references/audit-performance-operations.md)
- 文档、所有权与团队演进：[audit-evolution.md](references/audit-evolution.md)

完成条件：声明范围内已检查的每个问题都有账本项；需要不同裁决或动作的术语/版本/legacy 候选未被合并；重复位置无抽样截断；未检查区域和原因已记录。

### 3. 消解不确定性

先用仓库证据、历史、引用搜索和可运行验证消解 `Suspected`。剩余项若依赖产品意图、用户体验、外部消费者或所有权，全部写入报告“待用户裁决”，然后在主对话一次性提问。

例如 supervisor 主导调用 Claude Code/Codex 的系统中，又存在用户直调 CC/CX 的路径：先查产品文档、入口、遥测与测试；仍无法判断它是正式能力、兼容入口还是死路径时，记录问题并询问用户，不删除或固化猜测。

等待裁决期间继续处理互不依赖的工作；暂停所有依赖该裁决的删除、改名和行为变化。收到回答后把问题、答案、决策和受影响发现写回报告。

完成条件：每个 `Suspected` 已被本地证据转为 `Confirmed/Rejected`，或有明确问题等待用户；没有静默假设产品意图。

### 4. 排序并选择处理路线

使用 [prioritization-and-report.md](references/prioritization-and-report.md) 排序，但保留所有 Low/Info。轻量问题直接给最小安全动作，不制造系统地图或两个虚假方案。

G2 及以上读取 [treatment-playbook.md](references/treatment-playbook.md)。G3/G4 或“是否彻底重做”读取 [deep-modernization.md](references/deep-modernization.md) 并比较保留、止血、渐进重构、重新架构、重建/替换和退役。涉及 API、事件、配置、缓存、文件格式、数据库或历史数据时读取 [compatibility-data-migration.md](references/compatibility-data-migration.md)。

E0 到此进入总结。E1 到此冻结“修复前”章节，在主对话给出严重度表、七维评分、报告链接、建议修复范围和全部待裁决问题，然后等待用户确认。E2 可继续，但每个拟修改项都必须已有 Before 证据。

完成条件：每个拟处理项落在授权档位内，并有与风险相称的成功条件和验证方式；E1 已获得用户对修复范围及未决语义的确认。

### 5. 实施、验证与反哺文档

- E2 轻量分支实施可回滚的局部修复并运行针对性测试；E1 在用户确认后按批准范围实施；标准/系统分支先做一个代表性切片，再扩展。
- 逻辑与文档冲突时，先判断权威来源；明确 bug 应增加能失败的回归测试。产品语义不明时转为 `Suspected`，不把“保持兼容”误解为保留所有 bug。
- 每个变更保持单一主要意图，运行与风险相称的单元、集成、契约、迁移、性能、安全或端到端验证。
- 同步更新受影响的功能说明、示例、术语表、API/CLI 文档、架构决策和 runbook；记录没有可更新文档的情况。
- 将发现状态更新为 Fixed、Deferred、Accepted、Rejected 或 Open，保留修复前证据和实际验证结果。
- 冻结的 Before 数值不回写；在 After 中记录同口径 LOC、最大单元、测试/静态检查、发现处置、文档状态和行为结果，并解释每个差值。

完成条件：实现与授权一致；测试结果已写入报告；代码、测试和文档表达同一契约；剩余项仍完整可见。

### 6. 评分与对话总结

按 [prioritization-and-report.md](references/prioritization-and-report.md) 对 Security、Stability、Performance、Testing、Maintainability、Design、Release 分别给 0–10 分和证据置信度，计算 Overall。评分范围必须与报告范围一致，不把未检查写成满分。

主对话必须包含与报告一致的严重度表：

| --- | ---: | ---: | ---: |
| Critical |  |  |  |
| High |  |  |  |
| Medium |  |  |  |
| Low |  |  |  |
| Info |  |  |  |

随后给出评分块、最高优先级结论、已改内容、Before/After 对比、验证结果和 Markdown 报告链接。评分块每行必须包含恰好 10 个 `█/░` 字符、数值、等级和证据摘要，Overall 同样如此；不得在主对话省略条形图或用 `#`、`.` 替代。有待裁决项时紧接着列出全部问题。

完成条件：文件报告和对话数字一致；七项评分与总分齐全且每行条形图正好 10 格；每个未决 `Suspected` 已向用户提问；发生修改时 Before/After 同口径且差值已解释。

## 硬门禁

遇到以下情况先停止相关实施并请求用户确认：

- 升到 G3/G4 或 Q3。
- 升到 C2/C3、缩短兼容窗口，或删除公开 API、事件字段、配置键、数据库列、旧客户端支持与历史记录。
- 升到 D2/D3、接触真实数据或执行不可逆迁移。
- 删除文档、测试、示例或外部消费者仍声明的功能。
- 无法判断旧路径、`v2`、`legacy` 命名或直达入口是否承载产品语义/外部契约。
- 引入新运行基础设施、付费服务、跨团队契约或生产切流。
- 无法建立与风险相称的备份、恢复、验证或回滚路径。

安全漏洞、数据损坏和正在发生的生产事故优先止血，但只在用户授权的系统范围内行动。
